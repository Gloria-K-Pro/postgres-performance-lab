# Reflection

Working through this performance lab reinforced several practical lessons about database optimization and operational choices.

Using EXPLAIN ANALYZE made it abundantly clear how the planner executed the aggregation and where time was being spent. The `before` plan showed a full sequential scan over the `orders` table with a filter on `status` and `created_at`. That scan produced thousands of filtered rows and required reading table pages for the entire dataset, which translated directly into longer execution time and higher buffer activity. By contrast, the `after` plan showed an index-based access path that allowed the planner to locate recent `pending` rows quickly and avoid touching unrelated pages.

Indexing improved performance by enabling targeted data access. A partial composite index on `(created_at DESC, customer_id)` with `WHERE status = 'pending'` provides two advantages: it limits the index to the rows relevant to the query predicate (making the index smaller and more cache-friendly) and orders by `created_at`, which benefits queries constrained to recent data. The trade-offs are the additional storage and maintenance cost on writes — for write-heavy systems the cost of maintaining indexes must be balanced against read performance needs.

The isolation-level experiments highlighted the conceptual difference between statement-level and transaction-level snapshots. `READ COMMITTED` updates the snapshot per statement, so a long-running transaction can observe changes committed by other transactions between statements. `REPEATABLE READ` (snapshot isolation) pins a transaction to a single snapshot for its lifetime, providing repeatable reads across multiple statements but potentially masking later commits until the transaction ends. The practical surprise was how easy it is to introduce subtle bugs when application logic implicitly assumes visibility semantics; explicit transaction boundaries and the correct isolation level are essential.

Connection pooling is crucial for scaling a database-backed application. Creating many direct Postgres connections is costly in memory and CPU; PgBouncer reduces that overhead by multiplexing client connections onto a smaller set of server connections. Transaction pooling is often the right default for web apps because it maximizes connection reuse, but session pooling remains necessary when the application depends on connection-local session state.

The most valuable part of the lab was the combination of hands-on EXPLAIN ANALYZE investigation with a concrete optimization (partial composite index) and seeing the measured improvement. The end-to-end workflow — identify, instrument, change, re-measure — is directly applicable to production performance troubleshooting.
